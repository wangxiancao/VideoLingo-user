# ForceAligner stays on transformers; self-developed aligner engine declined

Status: accepted (2026-10-23)

The engine line is delivered through M2 plus the T4 seam (`glm_asr_native` in the ASR backend factory, transformers fallback retained; the default backend remains the transformers path until the T9/V4-8 switch decision). The remaining engine milestone M3 — a self-developed C++/CUDA inference engine for the official Qwen3-ForcedAligner-0.6B weights — is declined by the maintainer; word-level alignment stays on the official transformers path. Rationale: the maintainer-confirmed ASR-only target of 266 RTFx (#38) passed formal acceptance at 13508.5 ms = 266.5 RTFx (real 1 h audio, exclusive GPU, 3-run median, 13600 ms gate PASS, `bench/results/native-asr-m1/real-1h-accept-13600-PASS.json`); the end-to-end clause measured 27.41 s = 131.3 RTFx (< 540), of which the transformers aligner accounts for only 6.14 s (`docs/agents/native-asr-m2.md` §0); the Q3 quality gate passed (FP16 vs BF16 character match 99.468%, threshold ≥99%); and the transformers path's measured b20 peak of 10,300 MB allocated fits the 24 GB budget (`bench/results/t2b/zh_real_600s_pi-b20.json`). The aligner is therefore on no confirmed critical path. Reopening conditions, each of which requires a new spec rather than a quiet amendment of this ADR: an 8 GB deployment profile that cannot host the transformers stack; alignment becoming the end-to-end bottleneck; or a requirement to co-reside the aligner with the ASR engine in one resident process. This decision does not change the transcript contract — word-level timestamps remain ordered, monotonic, and in-chunk — and does not affect the optional zero-change 540 rerun on RTX 5090 documented in #38.
